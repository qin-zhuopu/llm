# Schema redesign and LLM-driven YAML regeneration for model data quality

This change redesigns the model.schema.json to focus on training details, tech stack, benchmarks, and API access — shifting away from the HuggingFace model-card alignment. It deletes 11 model entries whose markdown source was useless scraped fragments (navigation links, login prompts), fixes the `extract_yaml.py` prompt to better describe nested object schemas and handle common LLM output errors, and regenerates all 65 remaining YAML files through LLM extraction. Validation passes 100% (up from 29%). Watch for: the regeneration produced longer descriptions and capabilities but **dropped most optional metadata fields** (confirmed) — release_date, website, tags, access, region are missing from 70-80% of files, and the new schema's high-value fields (training, tech_stack, benchmarks, datasets) are populated in fewer than 5 files each despite being the stated motivation for the redesign; one file (Med-PaLM 2) lost concrete benchmark data that existed in the original and replaced it with vague marketing language from a scraped generic landing page (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The schema redesign pivots from HuggingFace metadata conventions toward training-centric fields (training stages, tech_stack, benchmarks, datasets, API info). But these new fields exist almost exclusively in the example file; fewer than 8 of 65 production YAML files populate any of them.

The extract_yaml.py prompt instructs the LLM to "strictly only output schema-defined fields," which combined with uninformative markdown sources means the LLM omits anything it can't extract — including fields it could have preserved from the existing YAML. The script has no merge-with-existing logic.

The net effect: descriptions and capabilities became richer and more specific, but substantial metadata regressed. 70 files lost `release_date`, ~50 lost `website`, ~46 lost `access`, ~57 lost `region`. The new high-value fields that justify the schema change are almost never filled. Quality score improved numerically because validation now passes, but information density decreased for many entries.

Three files now claim `release_date: 2026` because the LLM confused the markdown scrape timestamp ("抓取时间: 2026-08-25") with the model's release date.

## Information regression in regenerated files

The script regenerates YAML purely from the markdown file content, with no mechanism to preserve or merge existing YAML values. When the markdown source is a generic landing page (Med-PaLM 2's `.md` is Google Health's homepage: "Helping billions of people be healthier"), the LLM produces generic descriptions. Any concrete data that existed in the old YAML — because a human put it there — is lost.

Specific cases:

- **Med-PaLM 2**: status changed from `research` to `released` (incorrect — it's still research-only), lost `parameters: unknown`, lost the arxiv paper reference (`https://arxiv.org/abs/2305.09617`), gained a broken relative URL. The 86.5% MedQA accuracy — the most concrete quality signal in the entire dataset — is gone.
- **ChatLaw**: enriched description (correctly identifies MoE architecture, knowledge retrieval), but lost `release_date`, `website`, `access`, `region`, `tags`.
- **KPMG AI**: gained a rich multi-sentence description and product-specific capabilities. Lost `release_date`, `access`, `region`, `tags`.

The pattern is consistent: richer prose in `description` and `capabilities`, wholesale loss of structured metadata.

## Hallucinated dates

The markdown headers contain "抓取时间: 2026-08-25" and the LLM produced:

- `domains/media-entertainment/jasper-ai.yaml`: `release_date: 2026-08` (was `"2022"`)
- `domains/logistics-supplychain/sf-tech-ai.yaml`: `release_date: '2026'` (was `"2023"`)
- `domains/media-entertainment/yuewen-miaobi.yaml`: `release_date: '2026'`

Jasper launched in 2021-2022; SF Tech's logistics AI predates 2026. The extraction prompt should explicitly instruct the LLM to ignore scrape metadata headers.

## Schema redesign gap

The `description` field's `minLength` was raised from 10 to 30 characters, which alone would fail 90% of the old files and explains the bulk of the old validation failures. The example file (`schema/example.yaml`) demonstrates BloombergGPT with training stages, FinPile datasets, FPB/FiQA benchmarks — but it is the only file that actually demonstrates the new schema's capabilities.

Out of 65 production files:
- `training:` — 2 files (HuatuoGPT, one other)
- `tech_stack:` — 4 files
- `benchmarks:` — 1 file (HuatuoGPT)
- `datasets:` — 2 files
- `api:` — 1 file
- `parameters:` — 8 files
- `architecture:` — 10 files

The vast majority of regenerated files contain only the 7 required fields.

## extract_yaml.py: colon-fixing regex limitation

The YAML error recovery regex (`^(\s*-?\s*\w+:\s+)(.+)$`) will misfire on multi-line strings or flow-style YAML. For single-line key-value output from an LLM it's adequate, but if the prompt or model ever produces block scalars, this fallback will corrupt them.

## Test coverage gap

No automated tests exist for `extract_yaml.py`. The validation script checks schema conformance but not data quality — it cannot detect that a `description` is marketing fluff, that `release_date` regressed from a known value, or that a URL is a broken relative path. The quality score metric (41.7→65.9) is referenced but its implementation is not part of this diff.
